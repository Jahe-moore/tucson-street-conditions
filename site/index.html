Built on the City of Tucson's own public data

Which streets are worst, and who gets to see what?

Tucson publishes a condition score for every street it maintains. I built the system a city IT team would run on it: a script that pulls the data every night, a SQL Server database that checks it, and a Power BI report where each council office sees only its own ward.

Why this matters in Tucson

The city is spending $590 million fixing streets, worst first.

Voters passed Proposition 411 in 2022 to repair city streets. The commission overseeing it picks projects mainly by the lowest condition score, so the scores decide where the money goes. Three groups lean on that same data every week.

Ward council offices

Residents call about their street. Staff need to know how their ward compares and which of their streets are next in line.

Pavement program staff

They build the worst-first list, and need to skip streets that were just repaved and catch scores that are out of date.

Utility crews and the permit desk

A newly paved major street can't be cut for five years without extra restoration work. Crews need to know before they dig.

Sources: KGUN 9 on worst-first · oversight commission materials · City of Tucson right-of-way guide

How it works

Five steps, every night, with nobody touching it.

1. Pull PowerShellREST API

Asks the city's ArcGIS service for street condition and moratorium data, 1,000 rows at a time. Retries if the service hiccups. At night it asks only for what changed.

2. Stage SQL Server

Drops the raw rows into a holding table exactly as they arrived, so a bad download never touches the real data.

3. Clean and merge T-SQL

Fixes known problems (county districts in the ward field, 1900 used as "unknown"), then adds new streets, updates changed ones and records every score change.

4. Check Data quality

Ten checks after every load. A partial download or an impossible score fails the run; stale or missing data is flagged for the GIS team.

5. Report Power BIArcGIS

A ward scorecard, the worst-first list and a data health page, limited by ward. A map colored by condition.

Who sees what

Each council office sees its own ward. Engineers see the whole city.

The rule is enforced in two places. The database itself filters rows by who is asking, so it holds no matter what tool someone connects with. The Power BI report has matching roles, including one that reads each person's wards from a table, so adding a staff member is one row, not a new report.

Under the hood

Built to be run by someone else.

Rerun safely

Running it twice changes nothing

Each row carries a fingerprint of its values. A second load of the same data reports 11,655 unchanged and writes nothing.

Change history

Trend the city's layer can't show

The city keeps only today's score. Every time a score changes, the old and new values are saved, so trend builds up night by night.

Fails loudly

A bad night doesn't slip through

If a download comes back 10% smaller than last time, or a score is out of range, the run is marked failed and the log says why.

One log row per layer

Easy to answer "did it run?"

Start, finish, rows read, new, changed, unchanged, status and error message for every layer, every night.

Scheduled

Nightly and weekly

Only the changes every night at 2:15, the whole layer every Sunday so streets the city removed get flagged.

Tested

16 automated tests

Unit tests for the PowerShell functions, and database tests that build a throwaway copy, load sample streets and check the merge, history, checks and security.

What it can't tell you

  • Costs. The data has pavement area but no repair prices, so no dollar figures here.
  • How fast streets get worse. That needs the score history this system has only started collecting.
  • How the city's staff work today. The current-process map is my assumption, to confirm with them.
